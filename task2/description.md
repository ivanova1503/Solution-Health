
## 1. Обзор целевой архитектуры
Новая архитектура строится на принципах **API-First** и **Event-Driven**.

**Ключевые изменения и новые компоненты:**
*   **Мобильное приложение** — новый внешний актор для пациентов.
*   **API Gateway** — единая точка входа для мобильного приложения. Обеспечивает безопасность, маршрутизацию и защиту от перегрузок (Rate Limiting).
*   **Слой кэширования (Redis)** — для быстрого чтения расписания и снижения нагрузки на базу данных.
*   **Шина событий (Kafka / Брокер сообщений)** — для надежной асинхронной передачи данных между системами (анализы, уведомления, платежи).
*   **Anti-Corruption Layer (ACL) / Адаптеры** — прослойки для интеграции с legacy-системами (1С, LIS), чтобы защитить новые сервисы от сбоев старых систем.

## 2. Выбор паттернов и архитектурных стилей

| Интеграция / Поток данных | Паттерн и стиль | Обоснование|
| :--- | :--- | :--- |
| **Мобильное приложение ↔ Бэкенд** | **API Gateway + REST/gRPC** (Синхронный) | Мобильному приложению нужен мгновенный ответ (например, при поиске слотов). Шлюз скрывает сложность микросервисов, обеспечивает авторизацию (OAuth2) и защиту от спайков (Rate Limiting). |
| **Запись и Оплата (Транзакции)** | **Saga (Оркестрация) + Idempotency Key** | Пациент не должен записаться дважды или потерять деньги. Шлюз генерирует уникальный ключ идемпотентности, а паттерн Saga гарантирует, что если оплата не прошла, запись отменяется (компенсирующая транзакция). |
| **Передача результатов анализов (LIS → CRM → Приложение)** | **Event-Driven (Событийно-ориентированный)** через Kafka | Сейчас LIS шлет данные по FTP, что ненадежно. Переход на события (Event) гарантирует доставку (at-least-once). Если CRM недоступна, данные не потеряются, а «дождутся» в шине. |
| **Интеграция с 1С (Полисы)** | **Anti-Corruption Layer (ACL) + Circuit Breaker** | 1С часто падает и меняет формат ответов. Слой ACL изолирует новые системы от «плохого» дизайна 1С. Circuit Breaker (предохранитель) перестанет слать запросы к 1С, если она зависла, и быстро вернет ошибку пациенту. |
| **Уведомления (Push/SMS/Email)** | **Асинхронный (Pub/Sub) через Kafka + DLQ** | Отправка пушей не должна заставлять пациента ждать. События об записи или готовности анализов падают в шину, а сервис уведомлений разбирает их. Dead Letter Queue (DLQ) спасет от потери сообщений при перегрузках. |
| **Чтение расписания (поиск слотов)** | **Кэширование (Cache-Aside) через Redis** | Чтобы база данных расписания не падала от 50 000 пользователей, мы кэшируем свободные слоты. 99% запросов на чтение будут обслуживаться за миллисекунды без обращения к БД. |
