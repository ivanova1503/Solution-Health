**Цель:** Определить план горизонтального масштабирования для двух самых критичных систем «Здоровье+», чтобы выдержать 50 000 пользователей в час пик с откликом менее 1 секунды.

## Таблица стратегий масштабирования

| ИТ-система | Реализация горизонтального масштабирования | Ограничение выбранного метода | Описание решения для ограничения |
| :--- | :--- | :--- | :--- |
| **1. Сервис Расписания** (микросервис + PostgreSQL) | **Масштабирование приложений + Репликация БД.**<br>Запуск нескольких экземпляров приложения (Kubernetes) за балансировщиком. Создание реплик базы данных (Master для записи, несколько Replicas для чтения). | **Задержка репликации (Replication Lag).**<br>При записи (бронировании) данные могут не успеть обновиться в реплике, и другой пациент увидит слот как свободный (риск двойной записи). | **Маршрутизация запросов.**<br>Запросы на бронирование и чтение сразу после бронирования направлять строго на Master-базу. Для поиска слотов использовать кэш (Redis) и Read Replicas. |
| **2. 1С: Полисы** (Legacy-монолит) | **Масштабирование слоя интеграции (Адаптеров).**<br>Сам монолит 1С масштабировать сложно. Мы запускаем несколько экземпляров HTTP-шлюза (Адаптера) за балансировщиком для распределения входящих запросов. | **Узкое место в ядре 1С.**<br>Сколько бы адаптеров мы ни запустили, сама база данных 1С всё равно упадет при нагрузке выше 50 RPS. | **Кэширование и Очереди.**<br>Внедрение Redis для кэширования результатов проверки полисов (на 15 минут) и Kafka для буферизации запросов с жестким лимитом (Rate Limiter) в 40 RPS перед 1С. |


### Пояснение (почему выбраны эти системы)
**Сервис Расписания:** Это «лицо» мобильного приложения. Если он будет тормозить, пациенты просто закроют приложение. База данных без реплик ляжет от 50 000 одновременных запросов на чтение.

**1С:** Это самое слабое звено. Классический legacy-монолит невозможно просто «размножить» (скопировать) на серверах, поэтому мы масштабируем «обертку» вокруг него и защищаем его кэшем и очередями.
